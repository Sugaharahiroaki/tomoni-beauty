# ホットペッパービューティー／SALON BOARD 連携の調査報告と実装方針

調査日: 2026-10-18（Web調査。一次資料が無い点は「未確認」と明記）

## 1. 結論

- **一般公開の予約API・開発者向けパートナー制度は見つからなかった。** リクルートWEBサービスに現在掲載されているのは「ホットペッパーグルメ」のAPIのみで、ビューティー／サロン／予約に関するAPIは無い（旧 api.hotpepper.jp は 2023/10/31 に終了）。2007年当時は「ホットペッパーBeauty API」が存在したと報じられているが現在は提供されていない。
- SALON BOARD の公式ページに「連携サービス一覧」「外部連携API」の記載は無い。Airレジ・スマレジ等との連携は第三者記事に見られるが、公式一覧での裏付けは取れなかった。他社ツールの「サロンボード連携」は、顧客一括登録用ファイルを管理画面に投入する方式で、APIではない。
- **スクレイピング・自動操作は行わない**（指示どおり）。HOT PEPPER Beauty 利用規約（2023/11/23改訂）第5条は「当社の承認した以外の方法により本サービスを利用する行為」「商用目的で利用する行為」「無断で改変する行為」を禁止しており、自動操作は抵触し得る。SALON BOARD の掲載サロン向け約款は公開ページが見つからず未確認。

## 2. 現実的な連携手段（採用順）

### 2.1 LINE → 予約ページへの誘導（実装済み）

- 美容師ごとに **スタイリスト指名予約URL** を登録（`Stylist.hotpepper_url`）。実ページから観測されたURLの形:
  - サロン: `https://beauty.hotpepper.jp/slnH000000000/`
  - スタイリスト: `https://beauty.hotpepper.jp/slnH000000000/stylist/T000000000/`
  - 指名予約: `https://beauty.hotpepper.jp/CSP/bt/reserve/?storeId=H000000000&stylistId=T000000000`
  ※公式仕様ではなく観測値のため、予告なく変わり得る。アプリは URL をそのまま保存して使うだけなので形式変更の影響は受けない。
- LINE文面に埋め込む際は `/r/<code>/` の **クリック計測リンク** に置換（`TrackedLink` / `LinkClick`）。実績画面でクリック数を表示。
- 第2段階: リッチメニューの「予約する（ホットペッパー）」ボタンにも同じ計測リンクを使う。

### 2.2 予約情報の取り込み

| 方法 | 状態 | 備考 |
| --- | --- | --- |
| 手入力 | **実装済み（第1段階）** | 予約一覧から登録。案内後14日以内なら自動で帰属。来店化 → 録音へ |
| 予約通知メールの自動解析 | 第2段階（第一候補） | 下記 2.3 |
| 予約データのCSV出力 | 第2段階（補助） | SALON BOARD 機能一覧に「予約情報をデータで出力できます」と明記あり。手動エクスポート → アプリにアップロード → 名寄せ、という半自動ルートが取れる。顧客台帳のCSV出力可否は未確認 |

### 2.3 予約通知メール取り込みの設計（第2段階）

調査で分かったこと:

- 通知先は SALON BOARD の【設定】→【基本設定】→「予約お知らせメール一覧」で登録。登録アドレスには **認証メール** が届き、認証完了まで通知は届かない。
- 設定は **サロン（アカウント）単位**。スタイリスト個人に自動で届く仕組みは無い → 店側に「転送設定」または「通知先に専用アドレスを追加」してもらう必要がある（指示書の懸念どおり）。
- 他社ツール（サロンボードマスター等）は専用 Gmail を通知先に追加して巡回する方式を採っている。
- 届くのは予約とキャンセルの通知。本文には開始/終了時刻・お客様名（カナ）・指名有無・メニュー名が含まれると推測できるが、**送信元ドメイン・件名・本文の正式フォーマットは公式資料で確認できず**。実機で受信してヘッダーと本文を確認する必要がある。

設計案:

1. 美容師ごとに取り込み用アドレス（例 `resv+<stylist_key>@tomoni.example`）を払い出し、店側で SALON BOARD の通知先に追加、または既存通知の転送先に設定してもらう。
2. n8n の IMAP ノードで受信 → 件名/本文を正規表現で解析（フォーマットは実機サンプルで確定）→ `POST /internal/reservations/`（内部トークン認証、新規エンドポイント）。
3. アプリ側で `Reservation(source=EMAIL, customer_name_raw=カナ)` を作成し、`Customer.kana` / `name` と照合。一致候補が複数なら「要確認」として一覧に表示し、美容師がワンタップで確定。
4. 照合後は手入力と同じ帰属ロジック（`attribute_reservation`）で「案内→予約」を集計。キャンセル通知は `status=cancelled` に更新。
5. 解析失敗メールは原文を保持せず、件名と受信日時だけをログに残して手入力を促す。

## 3. 正式連携の継続調査

- リクルート（ホットペッパービューティー）の法人向け問い合わせ窓口に、API／データ連携パートナー制度の有無を直接確認することを推奨。公開情報では見つからなかったため、本アプリは当面「URL誘導＋メール/CSV取り込み」で進める。
- Google での予約（Reserve with Google）等、ホットペッパー以外の予約導線が増えた場合も、同じ `Reservation.source` の追加で対応できる。
